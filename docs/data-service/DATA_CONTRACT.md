# 데이터와 지표의 공통 계약

상태: 의미와 불변 조건을 정한 설계 초안. 실제 필드·SQL·API 스키마는 첫 분야에 맞춰 구체화한다. 아래 합성 예시는 출처와 무관한 검증용이며 플랫폼 데이터 사용 권한을 뜻하지 않는다.

## 1. 대상 식별

- 대상은 내부 ID와 `(source_code, source_native_id)`로 식별한다. 출처별 안정 ID는 고유해야 한다.
- 표기명·사용자명·URL 별칭은 변경 가능하다. 이름을 수정해도 새 대상과 분리하지 않는다.
- 서로 다른 출처의 대상은 이름이 같다는 이유만으로 합치지 않는다. 연결이 필요하면 검증한 외부 ID/명시적 관계와 근거를 둔다.
- 화면의 URL에는 비밀·사용자 인증값이 포함되지 않아야 한다. 사용자 입력 URL은 허용한 형식에서 ID를 추출하는 용도로만 사용한다.

## 2. 시간과 기록 단위

| 개념 | 의미 |
|---|---|
| `scheduled_for` / 수집 구간 | 예정된 작업의 정체성; 실제 데이터 기준 시각이 아님 |
| `retrieved_at` | 출처로부터 실제 응답을 받은 시각 |
| `source_as_of` | 출처가 제공한 수치의 기준 시각; 없으면 null |
| `period_start/end` | 구간 통계의 대상 기간; 해당할 때만 있음 |
| `time_basis` | 원천 기준 시각인지 수집 당시 관측인지 표시 |
| `computed_at` | 가공을 실행한 시각; 데이터가 최신이라는 근거가 아님 |
| `expires_at` | 해당 데이터의 보관/이용 만료 시각 또는 정책상 별도 근거 |

DB 내부 시각은 시간대가 있는 UTC로 저장한다. 표시 시간대와 일/월 경계는 분야 명세에 적는다. 원천이 날짜만 주면 그 정밀도를 보존하고 임의의 초 단위 정확성을 만들지 않는다. 출처가 기간 통계를 주는 경우 기간을 수집 시각으로 대체하지 않는다.

예정 작업이 하루 늦게 실행됐다고 전날 관측을 만든 것으로 기록하지 않는다. 과거 조회가 실제로 가능한 출처에서 받은 과거값만 역사 데이터로 인정한다.

같은 수집 구간의 재시도는 같은 관측을 중복 생성하지 않는다. 다음 구간에서 실제로 다시 확인한 값이 같다면 새 구간의 관측은 존재할 수 있다. 숫자가 같다는 이유로 서로 다른 날의 관측을 제거하지 않는다.

같은 구간에 정정된 값이 오면 버전/정정 기록과 출처의 수정 규칙에 따라 처리하고 관련 계산을 무효화한다. 최신 유효 관측과 과거 수정 내역의 공개·보관은 출처 정책 범위에서만 허용한다.

## 3. 수치의 종류와 품질은 별개

| 필드 | 값 예 | 규칙 |
|---|---|---|
| 종류 `kind` | observed / derived / estimated | 관측인지 계산인지 추정인지 표시 |
| 가용성 `availability` | available / missing / restricted / not_collected / insufficient_history | null의 사유를 잃지 않음 |
| 신선도 `freshness` | fresh / stale / unknown | 출처 기준 시각과 허용 지연을 이용. 계산을 새로 했다고 fresh로 바꾸지 않음 |
| 품질 사유 | source_correction / definition_changed / zero_baseline / partial_coverage 등 | 사용자 설명으로 변환 가능해야 함 |

실제 enum 이름은 분야 명세 때 고정하되 의미를 합치지 않는다. 값이 있어도 stale일 수 있고, derived도 충분한 근거로 정상 계산될 수 있다. estimated와 low_quality를 같은 뜻으로 취급하지 않는다.

`0`은 정상적으로 관측되거나 계산된 0이다. `null`, 비공개, 미수집, 호출 실패, 이력 부족은 0이 아니다. 반올림된 출처 값은 그 정밀도를 표시한다. 단위·통화가 다른 값을 변환 근거 없이 합산하지 않는다.

누계 수치가 감소하면 음수를 무조건 지우지 않는다. 정정·삭제·집계 기준 변경 가능성을 표시한다. 허용 여부와 표현은 지표별로 정의하며, 감소를 신규 활동량이 음수라는 뜻으로 해석하지 않는다.

## 4. 지표 계산

지표 정의에는 key, version, kind, 단위, 입력, 기간, 비교군, 공식, 반올림, 결측 처리, 공개 조건이 포함되어야 한다. 계산 코드와 화면 설명은 같은 정의를 사용한다.

단순 변화의 예:

```text
변화량 = 종료 관측값 - 시작 관측값
증감률(%) = (종료 관측값 - 시작 관측값) / 시작 관측값 × 100
```

시작값이 0이면 증감률은 `null`과 `zero_baseline`; 변화량은 계산할 수 있다. 두 시점의 누계 차이를 구했다고 전체 기간의 일별 값이나 정확한 원인을 알 수 있는 것은 아니다.

기간 계산에는 유효한 기준점 두 개와 지표 정의상 허용한 최대 시간 오차가 필요하다. 기준점 선택은 각 목표 시각 이하의 가장 가까운 유효 관측을 기본안으로 삼고, 목표 시각과 너무 멀면 계산하지 않는다. 선택된 실제 기준점·간격을 함께 제공한다. 미래값 선택이나 무음 보간은 하지 않는다.

허용 시간 오차·최소 표본 수·원천 의미 변경 경계는 `DOMAIN.md`에서 정한다. 미정이면 해당 기간 계산은 준비되지 않은 상태다. 출처·정의·단위가 중간에 바뀌면 동일 시계열로 연결하지 않고 표시를 구분한다.

평균·비율·순위에는 대상 목록, 제외 조건, 기간, 표본 수가 필요하다. 순위 모집단은 실제 추적 대상임을 표시한다. 모든 대상을 수집했다는 근거 없이 플랫폼 전체 순위·전체 평균이라고 쓰지 않는다. 일부 수집 실패로 비교군이 바뀌면 이를 표시하거나 발표를 보류한다.

추정 지표는 방법과 가정을 적고 관측값과 구분한다. 예측 범위를 제공할 근거가 없으면 정밀한 범위나 확률을 꾸미지 않는다. LLM 응답을 사실값·지표·인과 설명으로 바로 저장하지 않는다.

## 5. 재현성과 정정

계산 결과는 입력 관측 또는 입력 구간/버전을 추적할 수 있어야 한다. 같은 유효 입력과 같은 지표 버전은 같은 결과를 내야 한다. 화면에만 별도 공식을 작성하지 않는다.

공식 변경은 새 버전으로 다룬다. 비교 기간에 버전이 섞이지 않도록 허용된 원천으로 다시 계산하거나 버전 차이를 표시한다. 입력 만료 이후 재계산이 불가능하면 그 한계를 기록하며, 재현성 확보를 이유로 보관 조건을 어기지 않는다.

원천 오류 정정·삭제·만료로 결과가 바뀌면 조회 결과와 캐시도 갱신한다. 재시도로 값이 중복 합산되지 않아야 한다. 성공 처리와 체크포인트 확정은 관측 저장과 원자적으로 수행한다.

## 6. 읽기 API 기본안

제안 경로이며 아직 없다. 도메인 확정 후 구체화하되 의미를 유지한다.

| 기능 | 제안 | 조건 |
|---|---|---|
| 탐색 | `GET /api/v1/subjects` | 검색/정렬/페이지 크기 상한, 안정적인 ID 보조 정렬 |
| 상세 | `GET /api/v1/subjects/{id}` | 최신 유효 정보와 출처·신선도 |
| 이력 | `GET /api/v1/subjects/{id}/history` | 허용 지표·기간·점 수 상한; 확보한 관측만 반환 |
| 비교 | `GET /api/v1/compare` | 최대 3개 기본안; 같은 지표/기간/비교 가능 조건 |

검색 결과 없음은 정상적인 빈 목록이다. 등록되지 않은 상세 ID는 404, 잘못된 매개변수는 명시적인 클라이언트 오류로 처리한다. DB 장애를 정상적인 빈 목록으로 숨기지 않는다. 읽기 요청은 새 수집 작업·외부 HTTP·LLM 호출을 일으키지 않는다.

최소 응답 의미 예시:

```json
{
  "subject_id": "synthetic-001",
  "metric": "count_change",
  "metric_version": "1",
  "kind": "derived",
  "value": 50,
  "unit": "count",
  "availability": "available",
  "freshness": "fresh",
  "reason": null,
  "basis": {
    "source": "synthetic",
    "source_url": null,
    "time_basis": "collected",
    "from": "2026-09-01T00:00:00Z",
    "to": "2026-09-08T00:00:00Z"
  },
  "computed_at": "2026-09-08T00:05:00Z"
}
```

실제 공개 관측에는 허용된 원문 링크를 제공한다. `fresh` 판정은 분야별 기준을 만족했을 때만 사용한다. 필드를 무작정 늘리지 않되, 종류·기준 시각·단위·결측 사유를 제거하지 않는다.

내부 실행 ID·지표 버전은 추적 가능하게 유지하되 사용자의 기본 화면을 내부 시스템 정보로 채우지 않는다. 필요하면 방법 설명이나 지원용 상세 정보에서 제공한다.

## 7. 최소 검증 예제

다음은 기능 의미를 검증하는 시나리오다. 구현을 그대로 복사한 테스트 대신 예상 결과를 기준으로 검사한다.

| ID | 입력/사건 | 예상 결과 |
|---|---|---|
| C01 | 같은 작업/구간을 같은 응답으로 두 번 처리 | 관측 수와 계산값이 증가하지 않음 |
| C02 | 다음 구간에 같은 값 100을 실제 재관측 | 두 구간의 관측 존재, 변화량 0 |
| C03 | 시작 100, 종료 150, 유효한 동일 단위/기준 | 변화량 50, 증감률 50% |
| C04 | 시작 0, 종료 50 | 변화량 50, 증감률 null + zero_baseline |
| C05 | 시작 관측 없음 또는 기준점 허용 간격 초과 | 기간 변화값 null + 이력 부족; 그래프를 생성하지 않음 |
| C06 | 원천 필드가 없거나 비공개 | null과 실제 사유; 0으로 저장하지 않음 |
| C07 | 누계 100 → 90 | 관측 감소를 보존/표시; 지표별 규칙에 따라 정정 주의 또는 계산 제외 |
| C08 | 중간 페이지 실패 뒤 재실행 | 이미 확정한 페이지는 중복 없음; 체크포인트 이후 재개; partial 상태 추적 |
| C09 | 오래된 관측으로 오늘 재계산 | computed_at만 바뀌며 데이터 기준일과 stale 상태 유지 |
| C10 | 같은 안정 ID의 이름 변경 | 같은 대상 이력 유지; 다른 출처 동명 대상은 자동 병합하지 않음 |
| C11 | 추적 대상 100개 중 유효값 80개 | 비교군과 제외 수 표시; 전체 플랫폼 통계라고 표현하지 않음 |
| C12 | 입력 만료·삭제·동의 철회 | 읽기·캐시·파생 결과에서 재노출 없음; 정책대로 삭제 |
| C13 | 수정된 원천값 또는 지표 새 버전 | 관련 결과만 재계산/무효화; 이전 정의와 몰래 혼합하지 않음 |
| C14 | 장애 HTML 또는 인증 오류 응답 | 정상 빈 데이터로 저장하지 않고 실패 기록 |
| C15 | 사용자 URL이 내부 IP 또는 비허용 호스트 | 외부 요청을 하지 않고 입력 거부 |
| C16 | 수집 동시 실행 또는 최대 요청 예산 도달 | 한 작업만 실행 또는 수집 보류; 웹 조회는 계속 동작 |

분야별로 해당 시나리오를 구체화한다. 보관/삭제 규칙이 필드마다 다르면 하나의 전역 보관 기간으로 대체하지 않는다.
