# 모델 비용을 줄이는 구현·검토 방식

## 목적과 한계

높은 성능의 모델은 제품 경계, 데이터 의미, 위험한 가정과 설계 변경을 판단한다. 구현 범위가 명확한 작업은 비용 낮은 모델로 진행한다. 문서가 판단을 전부 대신하지는 못한다. 첫 분야가 정해지면 분야별 계약을 한 번 더 검토해야 한다.

`xhigh`는 모델 이름이 아니라 추론 강도 설정이다. 모델을 바꾸는 것과 추론 강도를 낮추는 것은 별개의 선택이다. 사용 가능한 모델/강도는 계정과 UI에서 확인한다. 이 문서 작성으로 모델 설정을 변경한 것은 아니다. OpenAI는 복잡도에 맞춰 모델과 추론 강도를 선택하도록 안내한다. [공식 모델 안내](https://learn.chatgpt.com/docs/models)

## 작업별 기본 배분

아래는 비용 절감률을 보장하는 표가 아니라 작업 배분 제안이다.

| 작업 | 기본 역할 | 높은 성능으로 다시 볼 상황 |
|---|---|---|
| 첫 분야 선택, 핵심 질문, 지표/보관 계약 | 설계 모델 | 기본적으로 여기서 충분히 판단 |
| 범위가 닫힌 모델·쿼리·API·수집 구현 | 일반 구현 모델 | 계약 충돌, 여러 모듈 구조 변경, 원인 불명 실패 |
| 문구, 단순 화면, fixture 정리, 작은 수정 | 경량 모델 | 의미·데이터 흐름을 바꿔야 할 때 |
| 마이그레이션, 정정/삭제, 동시성 | 일반 구현 + 중요한 경계 검토 | 데이터 손실·재노출·중복 가능성이 남을 때 |
| 핵심 흐름 통합/첫 공개 검토 | 설계/검토 모델 | 데이터·운영 조건이 확정되는 지점 |

현재 공식 안내의 예시로는 Sol을 복잡한 구현, Luna를 좁고 반복적인 작업에 배치할 수 있다. 실제 사용할 때 제공 여부와 현재 안내를 확인한다. 특정 모델명을 저장소의 영구 규칙으로 고정하지 않는다. 모든 작업을 가장 낮은 모델로 보내 재작업이 늘어나면 비용 절감에 실패한 것이다.

## AGENTS.md의 역할

파일명은 기본 인식 이름인 `AGENTS.md`를 사용한다. 루트에는 짧은 공통 규칙과 읽기 경로만 둔다. 상세 설계와 작업별 예제를 전부 붙이지 않는다. Codex는 프로젝트 경로의 지침을 읽으며 기본 결합 크기 제한이 있다. [공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

문서의 역할은 중복하지 않는다.

- `AGENTS.md`: 작업 방식·공통 경계·문서 진입점.
- `DATA_CONTRACT.md`와 `DOMAIN.md`: 데이터의 뜻과 선택 분야의 값.
- `TASKS.md`: 결과물·허용 범위·완료 조건.
- `DECISIONS.md`: 왜 이 구조를 선택했는지와 열린 결정.
- `STATUS.md`: 지금 실제로 어디까지 완료했는지.

모델을 바꿀 때 대화 전체를 다시 설명하기보다 현재 상태와 작업 ID를 전달한다. 다만 문서의 미정 항목이 실제로 중요한 입력이면 생략하지 않는다.

## 다음 세션 — 분야를 정할 때

```text
AGENTS.md와 docs/data-service/README.md, STATUS.md를 읽어줘.
첫 분야는 [분야], 첫 사용자는 [사용자]로 검토하고 싶어.
TASKS.md의 P01을 진행해줘. DOMAIN.md에 핵심 질문과 출처의
실제 제공 범위, 저장·가공·공개 조건을 근거와 함께 기록해줘.
기획 후보와 확정 결정을 구분하고, 아직 앱 구현은 하지 마.
```

첫 분야가 여전히 미정이면 후보와 필요한 사용자 판단을 좁히는 작업까지만 한다. 임의의 분야를 선택해 모든 뼈대부터 만들지 않는다.

## 구현 세션 — 닫힌 작업 한 개

```text
AGENTS.md와 docs/data-service/STATUS.md를 읽어줘.
TASKS.md의 [작업 ID]를 구현해줘. 선행 조건과 실제 코드 상태를 먼저 확인하고,
해당 작업에 필요한 문서만 읽어줘.
명세와 범위 안의 구현 선택은 스스로 결정하고, 기존 무관한 변경은 보존해줘.
중요한 미정 사항을 추측해서 채우지 말고 영향과 필요한 결정을 설명해줘.
관련 완료 조건을 검증하고 STATUS.md에 결과와 다음 작업을 남겨줘.
이번 작업에 포함되지 않은 배포나 기능 확장은 하지 마.
```

사용자의 원래 요청이 여러 작업을 명확히 포함하면 그 범위 안에서 이어간다. 한 작업 템플릿을 불필요한 승인 절차로 만들지 않는다.

## 검토 세션 — 재설계가 아닌 증거 검토

```text
AGENTS.md와 STATUS.md를 읽고 [작업 ID/변경 범위]를 검토해줘.
DATA_CONTRACT.md의 관련 사례와 실제 diff, 실행 결과를 기준으로
잘못된 데이터 의미, 중복 수집, 부분 실패, 비용 무제한 증가,
만료·삭제 데이터 재노출, 기존 기능 영향이 있는지 확인해줘.
일반적인 스타일 지적이나 새 기능 제안보다 재현 가능한 문제를 우선해줘.
문제가 없으면 완료 근거와 아직 검증하지 못한 범위만 짧게 기록해줘.
```

같은 파일을 매 작업마다 높은 성능으로 다시 검토하지 않는다. 최초 지표/스키마 확정, I04의 데이터 생명주기, V01/R01의 통합 경계를 우선한다.

## 계획을 다시 검토할 조건

요구 데이터를 출처가 제공하지 않음, 의미가 다른 값을 같은 지표로 합쳐야 함, 새로운 계정/권한/요금제가 필요함, 저장/삭제 정책과 기능이 충돌함, 여러 계층의 계약을 바꿔야 함, 같은 핵심 실패를 근거 있는 수정 두 번으로도 해결하지 못함.

이 경우 실패 명령·입력·기대/실제 결과·원인 후보·이미 시도한 변경·필요한 결정만 묶어 전달한다. 문서에 맞추려고 테스트를 약하게 만들거나 출처 값을 조작하지 않는다. 모델 변경은 사용자가 선택하며 변경됐다고 가정하지 않는다. 영향을 받지 않는 허용 작업은 계속할 수 있다.

## 비용 기록

모델 이름이나 한 번의 응답 길이만으로 경제성을 판단하지 않는다. 완료한 작업당 총 사용량, 재시도, 수정/검토 시간, 실제 결함을 본다. 사용량 정보를 볼 수 없다면 임의의 금액·절감률을 만들지 않는다.

작업을 시작할 때는 연결된 문서와 파일만 읽고, 검증 통과 후 동일한 검사를 반복하지 않는다. 종료 보고와 상태 문서는 짧게 유지한다. 필요 이상으로 에이전트를 병렬 실행하지 않으며, 현재 문서는 다중 에이전트 실행 요청이 아니다.

개발에 사용하는 모델 비용과 제품 운영 중의 LLM/API 비용은 별도다. 이 제품의 핵심 수집·조회에는 LLM을 필수로 넣지 않는 것이 현재 기본안이다.
